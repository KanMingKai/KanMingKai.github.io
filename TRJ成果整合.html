問題拆解

把「各自修 bug」拆成系統性的根因

每次 CPU 過載，大家的處理方式都是找最近改過程式碼的人去降頻，但這只是治標。

觸發點
co-Drive 被砍了，CPU 還是爆了。

CPU 一爆，大家的反應都是找最近改過程式碼的人：「你這邊算太多，去砍。」輪到我，把 co-Drive 降頻之後 CPU 真的降下來了。但過幾週又爆了，換另一個人去砍。看了幾輪這個循環，我才意識到問題不是哪個人寫得不好，是整個系統裡每個功能都在重複算同一件事。

根本原因
不是效能問題，是每個功能都在重造輪子。

表面上看起來是 co-Drive 算太多，但實際情況是 co-Drive、RMA 這些側向功能各自用不同方式算軌跡，串接的時候還要重新對齊，串完之後又各自重複算一樣的東西。降頻只是把問題往後延，根本原因是架構上大家都在重造輪子。

行動與採用
大家各自都有任務，所以自己先做出來，再開接口讓同事導入。

我先拿 1600 公里的 FOT 資料統計過，發現所有側向功能其實只會遇到偏移和銜接這兩種狀況。接著把上下匝道、跟車過馬路、大車避讓這些情境，全部用同一套方法重做一次，自己先確認跑得通。等基礎穩了，才開發共用接口讓同事接入。

The Problem

為什麼這件事很難。

根本問題:架構混亂,各自為政。各功能團隊獨立開發軌跡規劃邏輯,沒有共用方法、沒有統一規格,導致功能之間無法平順銜接。

架構混亂(各用各的軌跡規劃方法)
↓
無法平順銜接 → 控制不穩定、需大量個案修補
↓
運算量爆表(重複邏輯、無法共用計算結果)
↓
加新功能困難 → 要重新實作、又要顧慮相容性
↓
新功能開發週期長、測試驗證成本居高不下
問題現象延伸影響
軌跡規劃方法不統一各功能用不同插值、不同座標假設銜接點跳變,需逐案修補
無共用運算基礎相似邏輯各自重複實作運算量重複累積,資源浪費
新增功能成本高每個新功能都要從頭建軌跡邏輯開發週期長,難以迭代
測試驗證困難每個功能行為各自不同,無共同基準測試覆蓋範圍大、驗證時間長
Architecture Decisions

這是架構師的工作。

這些決策在動手寫程式之前就必須回答,決定了後續所有實作的邊界與約束。

1共用介面定義:要讓 N 個功能都能呼叫,模組的輸出格式必須是什麼?
2軌跡連續性規格:需要 C0(位置)、C1(速度)還是 C2(加速度)連續?
3參數化策略:以時間積分還是距離參數化?各自的計算成本是什麼?
4Phase 邊界條件:每個功能切換點的合法入口狀態是什麼?誰負責驗證?
5計算預算分配:trajectory planning 與 control 各自的 latency budget?
決策 01

建立 trj 共用模組,定義統一輸出介面

  • 定義全局橫向偏移量 egoX 作為所有功能的共用輸出格式
  • 各功能只需告訴 trj「目標位移量」與「當前進度 s」,模組負責計算位置與朝向
效果各功能不需要知道彼此的內部邏輯,只需對齊介面規格。
決策 02

poly4 作為統一的平滑函數

  • 規格:C0 + C1 連續(起終點位置與速度均為 0)
  • 3 階只滿足 4 個條件(不足),5 階滿足 6 個(C2 多餘),4 階以最低複雜度滿足 5 個邊界條件
f(s) = 3s⁴ − 8s³ + 6s²
效果所有功能的軌跡銜接點自動平順,不再需要逐案調校。
決策 03

距離參數化(Scroll-based),非時間積分

  • 以行駛距離 s ∈ [0,1] 參數化軌跡,任意時刻 O(1) 單點查詢
  • 無需每幀對全段路徑積分
效果運算複雜度從 O(N) 降至 O(1),這是 TC277 從超載降至 37% 的關鍵。
決策 04

Phase State Machine,明確定義切換條件

  • 每個 phase 定義:合法前驅、轉換條件、trj 呼叫方式
phase_state_machine
NORMAL→DETECT→MOVE→PASS→RETURN→IDLE
↳ 取消→CANCEL→NEW_DETECT→NEW_MOVE
LFCP_NORMAL→LFCP_DETECT→LFCP_MOVE→LFCP_PASS→LFCP_RETURN→LFCP_IDLE↺
效果新增功能只需新增對應的 phase,不影響其他 phase 邏輯。

Capabilities

這個專案展示的能力。

01

介面定義能力

讓 N 個功能共用同一套輸出格式,各功能不需互相理解對方內部邏輯。

02

邊界條件設計

從系統層面規格化連續性需求(C0+C1),治本而非在實作層逐點修補。

03

Trade-off 決策

poly4 選 4 階而非 3 或 5 階,有明確的邊界條件數 vs 複雜度理由。

04

跨模組視角

同時看到功能層、規劃層、控制層的資訊流,找到跨層的失效點。

05

可擴展架構

新增功能只需定義呼叫介面,不修改現有任何邏輯。

Q & A

面試追問準備。

Q為什麼選 4 階而不是 5 階或 3 階多項式?
3 階只能滿足 4 個邊界條件,不足。5 階滿足 6 個,但我們只需要 C1 連續,C2 是多餘的複雜度,沒有對應的控制收益。4 階以最低複雜度滿足需求,是有根據的 trade-off,不是隨意選擇。
Q測試時間怎麼從 3 個月縮短到 1 週?
原本 N 個功能各自有一套軌跡邏輯,每次要驗證「這個功能的軌跡行為是否正確」。引入 trj 後,軌跡規劃的正確性只需驗證模組本身一次,N 個功能自動繼承,測試範圍大幅收斂。
QTC277 的運算量是怎麼從超載降到 37% 的?
兩個因素:一是消除重複計算(原本 N 個功能各自計算軌跡,現在共用一份結果);二是計算方式從每幀積分全段路徑(O(N))改為距離參數化的單點查詢(O(1))。嵌入式平台資源有限,這兩個優化效果非常顯著。
Q這個架構能繼續擴展嗎?
可以。新增功能只需:1) 定義目標位移量與觸發條件;2) 呼叫 trj 介面取得位置與朝向;3) 在 phase state machine 新增對應的 state。現有的所有功能邏輯完全不需要修改。
Q架構整合和寫 code 的差別在哪裡?
寫 code 是回答「怎麼實作」,架構整合是回答「要實作什麼、介面長什麼樣、誰依賴誰」。trj 模組的定義——輸出格式、參數化策略、連續性規格——這些決策在動手寫程式之前就必須完成,且決定了後續所有實作的邊界與約束。
