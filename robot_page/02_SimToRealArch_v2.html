模擬跑得好不算數,實機跑得好才算
Sim-to-Real 我的貢獻 · 可觀測 → 可驗證 → 可歸因

整套導航堆疊自 Isaac Sim 部署到廠區實機,目前 3 台運行中。落差一定會有,問題是 能不能指名道姓地說出它是什麼。所以我補的不是三個單點功能,而是一條把落差往下逼的動線: 先看得見機器人在想什麼,再一階一階往上驗把失敗範圍鎖住,最後查表追到根因並回歸。 下面這張圖把三件事畫在同一個畫面裡:左上是我看它的窗口,中間是系統本體與三層驗證迴路, 右上是每一種落差扎進來的位置。五顆按鈕依序按過去,就是這條動線走一遍。

1
STAGE 1 · OBSERVABLE

做出 IVI,隨時監控機器人視角 —— 馬上知道它為什麼左右轉

導航出問題時最貴的不是修,是猜。所以第一件事是做一支 接 rosbridge 的 Local Map View:把佔據網格、拓撲站點與連線、全域路徑點、 MPPI 最佳軌跡疊在同一張圖上,再用圖層開關一層一層剝開。 「它為什麼往左偏」不必用推的 —— 關掉障礙物層,看紅色那條軌跡還繞不繞就知道了。

沒有這個畫面
「它剛剛怪怪的,好像有點偏。」

沒有時間點、沒有模組、沒有數值 —— 這種描述無法立案,只能整條堆疊從頭猜起, 而且下次同一個現象還要再猜一次。

有這個畫面
「MPPI 最佳軌跡繞開了那個棧板,但全域路徑點沒動。」

局部規劃在做事、全域規劃沒反應 —— 還沒開始查,範圍已經縮到一個節點。

/target_station

指定站點編號直接下發 —— 這顆按鈕就是第 2 階 STEP 02「下站點」的操作入口。

/free_nav_request

任意 X / Y / Yaw,或直接在地圖上點 —— 對應 STEP 03「自由導航」。

/cmd_stop

任何一階跑歪都能當場收手。敢把階梯往上爬,前提是隨時停得下來。

同一個介面既是觀測台也是驗證的操作台 —— 第 1 階與第 2 階不是兩件事,是同一支工具的兩種用法。 (最底下那階的對位微調走 /finetune_cmd,不在這排按鈕上)

疊圖式監控

佔據網格、拓撲、路徑點、MPPI 軌跡在同一張圖上,現場看到什麼、機器人看到什麼可以直接對照

逐層剝開理由

圖層一層一層關掉,「為什麼往這邊轉」自己浮出來,不必靠推理

狀態機看得見

RE / LP / 結果三段狀態同時顯示,卡在路徑執行還是局部跟隨,一眼分得出來

能觀測也能下命令

站點、自由導航、緊急停止都在同一頁,不用開三個終端機才驗得了一件事

STAGE 2 · VERIFIABLE

把架構設計成可以驗證的:對位 → 下站點 → 自由導航

直接讓機器人跑自由導航,失敗了也說不出是定位、控制還是規劃的問題。 所以我把整條導航堆疊當成三層巢狀迴路來設計:對位是最內環、下站點包住它、 自由導航再包住外面。驗證順序就是由內而外把環一個一個關起來, 每關一層掛一個可量化的通過條件。 這樣「失敗時範圍鎖在那一階」不是宣稱 —— 是圖上看得出來的事實: 驗內環的時候,外面兩個環根本還沒接上。 跟車用 MIL / SIL / HIL 的分層邏輯是同一件事,也是控制設計裡 先把內環調穩再往外走的同一個做法。

可驗證架構的設計原則
  • 模組化設計,方便單點驗證
  • 可量化指標,驗證結果可衡量而非靠感覺
  • 由簡到難,逐步擴展能力邊界
  • 每一層都可獨立驗證與回歸測試
  • 確保 Sim 與 Real 行為一致,模擬結論才對實機有效
  • 失敗時範圍鎖在該階,不必全系統重查
RESULT

在真實環境中
穩定可靠運行 每晚 300 場景無人值守回歸,場景成功率 40% → ~100%; 目前廠區 3 台運行中。

3
STAGE 3 · ATTRIBUTABLE

解析 TF Tree 之類的底層,把 Sim-to-Real 的常見落差變成可查表的東西

落差不該每次都重新推理一遍。我把遇過的現象整理成 現象 → 原因 → 影響 → 對策 的對照表,分成三群:TF(座標與時間)、 DDS(通訊)、執行器(命令下發時序)。 表的價值不在完整,在下次遇到同一個現象時不必再猜 —— 查到哪一列,就回第 2 階跑哪一階的回歸。

LOOK-ALIKE

查表最容易踩的坑是兩個不同根因長得一模一樣: 單執行緒 executor 被長工作卡住,回呼延遲的外觀與 TF 延遲幾乎無法分辨。 差別在量哪一個數 —— 看 TF 的 stamp 差還是看回呼間隔。 分不出來就會整個查錯方向,所以表裡把它獨立成一列。

我的做法
  • 建立 TF Tree 檢查工具,自動化檢查連接關係與延遲
  • 可視化 TF 關係與資料流,讓斷鏈與時間錯位一眼看得出來
  • 把 QoS 與 domain 設定納入啟動檢查,不相容在起機當下就擋下來,而不是跑到現場才發現收不到
  • 建立 Sim vs Real 差異分析清單,現象進來先查表再開查
  • 持續優化,減少差異帶來的影響而不只是記錄差異
RESULT

縮小 Sim 與 Real 的差距,
提升實機表現穩定性 模擬的結論能拿來預測實機行為,模擬才算數 —— 這是整條動線存在的理由。
