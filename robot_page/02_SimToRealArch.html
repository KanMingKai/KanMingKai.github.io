模擬跑得好不算數,實機跑得好才算
Sim-to-Real · 可觀測 → 可驗證 → 可歸因

整套導航堆疊自 Isaac Sim 部署到廠區實機,目前 3 台運行。落差一定會有,問題是能不能指名道姓地說出它是什麼—— 所以我補的不是單點修正,而是三件讓落差無所遁形的基礎建設:看得見機器人在想什麼(可觀測)、 一階一階往上驗(可驗證)、每個現象都追到根因(可歸因)。

1

做出 IVI,隨時監控機器人視角——馬上知道它為什麼左轉

導航出問題時最貴的不是修,是猜。所以第一件事是把機器人的視角與決策理由攤在畫面上: 看得到前左右鏡頭、看得到規劃出來的路徑,更重要的是看得到「它認為自己該右轉」的四個依據與信心值。 從此問題定位不再從「我覺得它剛剛怪怪的」開始。

2

架構設計成可驗證的:對位 → 下站點 → 自由導航

直接讓機器人跑自由導航,失敗了也說不出是定位、控制還是規劃的問題。 所以驗證要有階梯:先驗最小的閉環,通過才准往上一階。 每一階都有可量化的通過條件,失敗時範圍自然被鎖在那一階裡——這是把車用 MIL / SIL / HIL 的分層邏輯搬過來的同一件事。

STEP 01
對位驗證
下 5 cm → Δx ≤ 5 cm · Δy ≤ 5 cm
  • 驗證定位精度
  • 驗證控制精度
  • 最小閉環驗證單元:命令下多少、實際走多少
STEP 02
下站點
直接到達指定站點
  • 驗證路徑規劃
  • 驗證避障能力
  • 站點到站點的連續精度
STEP 03
自由導航
任意座標任務 · 長時間運行
  • 驗證全域規劃
  • 驗證動態避障
  • 長時間穩定性驗證
可驗證架構的設計原則
  • 模組化設計,方便單點驗證
  • 可量化指標,驗證結果可衡量而非靠感覺
  • 由簡到難,逐步擴展能力邊界
  • 每一層都可獨立驗證與回歸測試
  • 確保 Sim 與 Real 行為一致,模擬結論才對實機有效
  • 失敗時範圍鎖在該階,不必全系統重查
3

把 Sim-to-Real 的常見落差拆成可查表的東西

落差不該每次都重新推理一遍。我把遇過的現象整理成現象 → 原因 → 影響 → 對策的對照表, 分成三群:TF(座標與時間)、DDS(通訊)、執行器時序(命令下發)。 表的價值不在完整,在下次遇到同一個現象時不必再猜。

TF Tree · 先確認這棵樹是對的

規劃輸出不進這棵樹。global_path / goal / local_path 是 topic 而不是 frame, 把它們畫進 TF tree 是常見的誤解——TF 只描述座標系之間的關係, 先把這件事講清楚,下面那張表才有共同語言。

我的做法
  • 建立 TF Tree 檢查工具,自動化檢查連接關係與延遲
  • 可視化 TF 關係與資料流,讓斷鏈與時間錯位一眼看得出來
  • 把 QoS 與 domain 設定納入啟動檢查,不相容在起機當下就擋下來,而不是跑到現場才發現收不到
  • 建立 Sim vs Real 差異分析清單,現象進來先查表再開查
  • 持續優化,減少差異帶來的影響而不只是記錄差異
RESULT

縮小 Sim 與 Real 的差距,
提升實機表現穩定性 模擬的結論能拿來預測實機行為,模擬才算數——這是整條閉環存在的理由。
