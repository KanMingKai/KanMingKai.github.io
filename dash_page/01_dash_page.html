THE PROBLEM
架構文件只要靠人維護，就一定會過期

團隊的架構圖與異動記錄，過去都靠人工維護：程式改完要另外寫一份變更說明，架構圖要有人記得去改。只要有一次沒跟上，之後就沒人敢信它。我的做法是讓兩份文件都不再靠記性——異動記錄交給 LLM 從 diff 產生，架構圖交給 CI 每天從原始碼重新解析，兩條流最後匯進同一個 Web Dashboard。

痛點 01
變更說明沒人想寫 改完一輪程式，還要回頭把「動了哪些節點、影響哪些 Topic」用人話寫一次。格式每個人不一樣，寫久了就開始省略。
痛點 02
架構圖跟不上程式 節點與 Topic 的連接關係一直在變，手畫的架構圖只要落後一版，讀的人就得回去翻程式，那張圖就等於不存在。

TWO STREAMS
一條靠人觸發，一條完全自動

兩條流唯一的交會點是「上色」：架構圖由 CI 決定長相，異動記錄只負責標出這次動到哪裡。兩者互不依賴，任何一條掛掉，另一條照樣有東西可看。

異動記錄流 · 人工觸發

開發者改完一輪程式後，不用手寫變更說明：從入口頁複製既定 prompt，交給 Claude Code 產生格式一致的 changes.json，儀表板直接吃這份檔案。

  1. 使用者開 index.html，複製 Copy Prompt
  2. Claude Code 讀 diff，輸出 changes.json
  3. change.html 呈現本次異動內容
  4. 異動涉及的節點／Callback 在右側兩張圖上上色
架構解析流 · CI 每日自動

架構圖不是人工維護的：GitLab CI 每天 09:00 掃過 amr_base_sw 原始碼，產出 topic_report.xlsx，前端再解析成節點與邊。

  1. CI 讀 Fih_amr_sw 原始碼（每日 09:00）
  2. 輸出 topic_report.xlsx
  3. arch_view.html 解析 xlsx，建立節點／邊
  4. 產生 Node-Topic Graph 與 Callback Graph

兩條流唯一的交會點是「上色」：架構圖由 CI 決定長相，異動記錄只負責標出這次動到哪裡。

ADAS → AMR
團隊要我把 ADAS 這套做法，搬到 AMR
