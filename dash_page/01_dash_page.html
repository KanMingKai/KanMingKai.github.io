自動維護 ADAS → AMR 反思
DATA FLOW · 核心
導入車用的嚴謹制度：文件從人工維護，轉為自動維護

這套規格是從車用搬過來的。ADAS 裡每條訊號進版本前都得先有一份 signal definition：名稱、型別、值域、更新週期。模擬驗證和 unit test 也直接照這份規格生測資。

到了 AMR，這份規格不再靠人填，改成系統統一自動管理：每天 09:00 由 GitLab CI 從原始碼重解一次，再畫成圖（概念接近 rqt_graph）。沒有人工這關，就不會有文件品質不一的問題。

另外我把架構拆成兩條分流，是為了省 Claude Code token，也為了管控輸出穩定性：程式架構關係用程式解析，同一份程式碼跑幾次都是同一張圖，一個 token 都不用花；LLM 只讀 diff，做它真正擅長的事，把改動翻成人話。整包原始碼丟給 LLM 畫架構也不是不行，但 token 燒不完，而且每次畫出來都不一樣。

兩條流唯一的交會點是「標注修改」：架構圖由 CI 決定長相，異動記錄只負責標注這次修改了哪裡。

ADAS → AMR
機器人現在用 MPPI，但我們團隊想把 ADAS 軌跡規劃的成功搬進 AMR 領域

MPPI 在非結構化環境、動態障礙物、算力放得下一顆 GPU 的時候是合理的選擇，機器人團隊用它有它的道理。我們這次的約束不同：運算力受限（嵌入式 MCU，固定週期內必須算完）、輸出必須穩定（同樣的輸入要給同樣的線，才回歸得了、才對得起客戶逐段追問）。這兩個條件把可選集合壓得很小——而三段式，是我在 ADAS 已經把這條路走完、並在 9 個功能、5 種車型上驗證過的那一個。
