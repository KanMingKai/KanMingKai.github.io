DEV PIPELINE · V 模型
V 模型全端研發與架構主導
端到端系統規劃、自動化 Topic 驗證與閉環測試

系統架構主導與規格定義：主導機器人系統的架構層規劃，包含節點職責定義、Topic / Msg 與 Action / Service 介面設計；AI 負責的是最底層的實作，每一層要驗什麼、介面長什麼樣，仍然得先由人定義。

自動化架構驗證與測試閉環建置：導入每日自動化 Topic Analysis 架構驗證與視覺化測試載具，讓動態節點圖與設計藍圖逐日對齊；同時建置隨機測試場景與夜間壓力測試閉環，把系統穩定度變成可追蹤的數字。

左臂往下定義、最底部實作、右臂往上驗證；中間三條橫線是「這一層驗的，就是左邊同一層的產出」。

DATA FLOW · 核心
導入車用的嚴謹制度：文件從人工維護，轉為自動維護

自動化架構解析與管線建置：設計並實作自動化分析工作流,由 CI Server 每日定時解析原始碼(產出 topic_report.xlsx),再由前端 Web Dashboard 動態生成 Node-Topic 拓樸圖與 Callback 觸發鏈,取代會過期的人工維護文件。

AI 輔助異動追蹤與協作：整合 AI 輔助工具(Claude Code)自動產出結構化異動記錄(changes.json),讓架構變更與程式碼實作即時對齊,跨團隊看的是同一份每日更新的事實。

兩條流唯一的交會點是「標注修改」：架構圖由 CI 決定長相，異動記錄只負責標注這次修改了哪裡。

SIM-TO-REAL · 落地
Sim-to-Real 系統整合與車規紀律導入
把 ADAS 的驗證標準跨域移植，擊破 AMR 實機落地瓶頸

精準診斷 Sim-to-Real 系統級痛點：AMR 在模擬環境裡收斂得很漂亮，搬上真機才發現問題不在演算法。跳脫演算法除錯的迷思，定位出三件系統整合與物理限制的問題：舊速度指令卡在 ROS 2 佇列裡，煞停慢半拍、當下看不到軌跡走得對不對、里程計回報的距離對不上實際位移。三個都不是規劃器算錯，是「來不及」、「看不見」與「對不準」。

跨領域導入車規級驗證與除錯紀律：右邊三個做法不是為這台機器人新發明的，是 ADAS 那邊已經在跑的紀律搬過來：把規劃結果疊回操作畫面、由下而上一層驗過才放行、場景庫全跑完才碰真機。同一套流程，換一個載體。

左欄（藍）是真機上量到的三個現象，右欄（綠）是接住它們的三個做法，兩欄各自編號 1 → 3。圖上的指令、站點代號與量測值維持原文（move 2.0、goto ST-02、SCN-0842）—— 那些是實際打進去的東西，翻成中文反而對不上。

ISAAC SIM · 24/7
研發效能優化與自動化驗證閉環
Isaac Sim 日夜壓力測試管線，零人工等待的迭代

自動化測試管線與日夜循環架構：上一節的「模擬先行」要划得來，前提是它不佔用人的時間。驗證因此被排成一天的循環：白天設計測試案例、跑常規驗證；夜間自動化壓力測試接手，在 Isaac Sim 裡跑 100~200 種任務組合去挑戰極限；早晨報告已彙整完成。

工程負擔解放與決策效率：換來的不是「機器不用睡」這種說法，而是把等結果這段時間從工作日裡挪走。工程師一坐下就看得到測試組數、失敗案例與 TOP 問題，右邊那四項價值都是從這一點長出來的。

左邊是一天的循環（白天 → 夜間 → 早晨），右邊是這個循環換來的四件事。
